## 5. Explanation of the 7 vs 10 Result

The frontend showing 7 user-selectable action types (instead of 10) is **intentionally correct** per the V3 architecture:

### Why each system-generated action must NOT be manually selectable:

| Action Type | Why It Cannot Be Manually Recorded |
|-------------|------------------------------------|
| `STATUS_CHANGED` | This action is a **side effect** of a direct status update via `PATCH /:id {status: X}`. The previous and new status values are captured by the backend (`existing.status` → `b.status`) and recorded automatically. If a user could manually POST `STATUS_CHANGED`, the `previous_status` and `new_status` fields would have to be trusted from the client — which would allow fabrication of historical state transitions. V3 forbids this; identity and state both come from the server. |
| `ASSIGNED` | This action is a **side effect** of the first assignment via `PATCH /:id {assignedTo: X}`. The backend determines whether to label the action `ASSIGNED` (was null) or `REASSIGNED` (was non-null) — see line 5325: `const actionType = existing.assigned_to ? 'REASSIGNED' : 'ASSIGNED';`. Allowing manual POST of `ASSIGNED` would break this invariant — the label is determined by the previous state of the row, not by user intent. |
| `REASSIGNED` | Same as above — determined by the prior state of `assigned_to`. |

### Summary

- **7 types are user-recordable outcomes** — they describe what the employee did (reviewed, contacted, etc.).
- **3 types are system-generated audit trail entries** — they describe what the system did in response to a PATCH. Their semantics are state-dependent and MUST NOT be client-supplied.

The frontend's split (7 user-selectable for the Action Recorder, all 10 covered in the Action History timeline via `ALL_ACTION_TYPE_KEYS` at line 122) is the **correct** interpretation of the V3 schema and endpoint design.

### Verification of No Unsafe Frontend Exposure

- `USER_ACTION_TYPES` (lines 103–111): exactly 7 types — matches `VALID_ACTION_TYPES` in backend line 5349.
- `ALL_ACTION_TYPE_KEYS` (lines 122–133): all 10 types covered for history rendering (display-only).
- The Action Recorder form (lines 1051–1054) iterates over `USER_ACTION_TYPES` only.
- There is no path in the frontend to submit `ASSIGNED`, `REASSIGNED`, or `STATUS_CHANGED` to `POST /actions`.

**Confirmed: no unsafe or invalid action is exposed to the user.**
